# skill-lifecycle-z 评测用例（自身）

> 本文件是 `skill-lifecycle-z` 自身的评测场景集合，供 `validate_skill.py --mode create` 硬门使用。
> 路由级回归测试（create/improve/vet 的 prompt → 子协议映射）另见包根 `test-prompts.json`（含 6 条已路由场景，含「项目入口型」这一分支）。

> ⚠️ **为什么前三个场景测的是「能不能干成事」，而不是「包自己健康吗」**：
> 只有元测试（自检全绿、能跑 vet）的话，一个「流程写得漂亮、用户一用就走错路」的 skill
> 依然能过门 —— 那测的是房子结不结实，不是住着舒不舒服。
> 场景4 保留一条元测试兜底。

## 场景1：把项目做成 skill 入口（happy path · 路由型）

- 输入：「我这个项目里文档和脚本都齐了，帮我做个 skill 当入口就行，不用把内容搬进来」
- 预期：
  1. 判为 **CREATE + 路由型**（不是 IMPROVE —— 东西还不存在；也不推给 `skill-creator` —— 有素材）
  2. **先问**：skill 放项目内还是用户级。这决定包外引用怎么写，选错装完就废
  3. SKILL.md 只含四样：触发条件 / 路由表 / 执行顺序 / 反模式。**不抄项目文档内容**
  4. 交付 `evals/basic.md`，含 **≥1 个反向场景**（不该触发时确实没触发）
  5. 跑 `validate_skill.py --mode create` 全绿才算完成
- 判错信号：把项目文档内容抄进 SKILL.md；跳过 evals 直接交付；不问放哪就写相对路径

## 场景2：说不清问题时该走哪条路（边缘场景）

- 输入：「这个 skill 用着别扭，帮我优化一下」（说不出具体哪里别扭）
- 预期：
  1. 走 **Step −1 判路径**：拿不出「哪个输入 → 哪个错误输出」→ 走**标准路径**（不是 FIX）
  2. 先造 3–5 个测试 prompt（含 1 个反向），跑出观察，**再**动手
  3. 每轮只改 1–2 个核心模式；改完先跑 `--mode improve`，再用同一批 prompt 对比 baseline
- 判错信号：不跑直接改；一次改一大堆；拿不出 before/after 就说「改好了」

## 场景3：反向 —— 这个请求不该归本 skill

- 输入：「帮我从零设计一个全新的 skill，我没有现成流程，也没有可合并的素材」
- 预期：判为**从零设计** → 明确交回内置 `skill-creator` 并说明理由；不硬接
- 判错信号：硬着头皮按 CAPTURED 编一套「痕迹」出来；或按模板造个空壳交差

## 场景4：自检全绿（元）

- 输入：在包根运行 `self_check.py`（直连源目录，或经 `~/.workbuddy/skills/` 的 symlink 视角）
- 预期：9 项全部 PASS、EXIT 0；覆盖 frontmatter 合法 / Reference Files 表双向齐全 / test-prompts 路由正确 / 无活跃 Claude Code 生态残留 / scripts 工具脚本齐全 / 文档-实现契约一致 / 红牌清单三处一致 / 同源检查清单逐条一致 / 包内互相引用无悬空
