# Skill Improve — 演进式 Skill 改进（参考协议，按需读取）

> **路径约定：** `<lifecycle>` 指本 skill 包根（定义见主入口 SKILL.md「路径约定」），脚本命令请直接替换为该路径。

> **核心哲学：好 skill 是总结出来的，不是设计出来的。**
>
> 不要试图一次性写出完美的 skill。先跑起来，观察真实表现，从失败中提炼模式，小步迭代。

**两个路径：**
- 🐇 **快速路径（FIX 模式）**：你带着具体问题来，改动局部、不涉及整体架构
- 🐢 **标准路径（完整演进循环）**：说不清哪有问题，需要深度迭代

---

## ⚡ Step −1：先判路径（不许跳过）

**动手前必须先回答一个问题：我能不能说出「哪个输入 → 哪个错误输出」？**

| 你手上的信息 | 走哪条 | 理由 |
|---|---|---|
| 一个具体失败案例（输入 + 错误输出） | **FIX** | 有靶子，不需要先观察 |
| 多个失败案例，但看不出共性 | **标准**（第③步替你归因） | 需要提炼，不是逐个修 |
| 只有「感觉不好用」，拿不出案例 | **标准**（第②步先造案例） | 连靶子都没有 |
| 问题明确，但属于结构层（职责太宽 / 太窄） | 先 FIX 局部 → 再评估是否要拆 | 结构问题改不动就得重做 |

**成本对比（决定这次值不值得跑循环）：**

| | 耗时 | 一轮改多少 |
|---|---|---|
| FIX | 几分钟 | 1 处 |
| 标准 | 每轮 40–70 分钟，至少 2 轮才谈得上收敛 | 1–2 个模式 |

> ⚠️ **最常见的浪费**：用户明说了「它总漏掉第 3 步」，却还是从「读全部内容、建立直觉」开始跑五步循环 ——
> 40 分钟后做完的事，等价于直接改那一段。
>
> **能一句话说清问题，就不要跑完整循环。**
> 观察是为了发现**你还不知道**的问题，不是为了确认**你早就知道**的问题。

---

## 🐇 快速路径：FIX 模式

**适用：** 用户说"这个 skill 生成的格式不对"、"它总是漏掉 X 步骤"、"这个引用过期了"。

### 步骤

1. **读取 skill** → 定位问题段落 → 理解 why
2. **诊断** — 对照下方问题分类表，定位失败模式（WorkBuddy 无 `dz benchmark`，靠人工观察 skill 实际输出 / 问题段落来归因；若环境另有评测工具可辅助，但不强制）
3. **分类问题** — 属于哪种类型？

   | 类型 | 表现 | 修复策略 |
   |------|------|---------|
   | 引用过期 | 引用不存在的工具/文件/路径 | 更新引用 |
   | 步骤缺失 | 关键步骤未写入协议 | 补充步骤 |
   | 指令模糊 | agent 执行时不确定怎么做 | 细化指令 |
   | 反模式缺失 | 无"NOT to use"指导 | 从失败中补充 |
   | Schema 不匹配 | 输出格式不符合预期 | 对齐 schema |

4. **针对性修复** — 最小改动，非完整重写
5. **重新验证** — 确认修复恢复了质量
6. **记录** — 为此次失败模式添加反模式条目

### 快速路径约束

- 只改与问题直接相关的段落
- 不顺手"优化"其他部分
- 改完建议用户试一下确认

---

## 🐢 标准路径：完整演进循环

**适用：** skill 有系统性问题、用户普遍不满意、或需要多轮迭代打磨。

**⚠️ 不适用：** 你已经有明确的失败案例 → 直接走 FIX（见 Step −1）。跑完整循环只在「不知道该修什么」时才划算。

方法论来自三个核心机制：

| 机制 | 含义 | 落地 |
|------|------|------|
| **OTF**（On-The-Fly） | 边跑边总结 | 每跑一个测试 prompt 就记录观察 |
| **JIT**（Just-In-Time） | 小步快跑 | 每轮只改 1-2 个核心模式 |
| **Bootstrap**（自举） | 知识自增殖 | 每轮笔记是下一轮的燃料 |

---

### 第一步：冷启动 — 建立直觉（5 分钟）

读取目标 skill 的全部内容（SKILL.md + references/scripts）。回答：

1. 这个 skill 的核心指令是什么？
2. 触发场景和边界在哪？
3. 哪些地方**直觉上可能有问题**？（模糊指令、缺失边界、过度工程、信息密度低）

把直觉记下来，但**不要急着改**。直觉只是假设，需要数据验证。

---

### 第二步：观察 — 用真实 prompt 跑 skill（10-20 分钟）

**选择 3-5 个测试 prompt：**
- 至少 1 个核心 happy path
- 至少 1 个边缘场景（含糊说法、不规范输入）
- 至少 1 个反向测试（skill 不该被触发）
- 用户带来的真实失败案例 → 最优先

**OTF 要求：每跑完一个 prompt，立即记录观察**（不等全部跑完）。

**工作目录放哪（这条别含糊）：** 放在**被改 skill 之外** —— 写进 skill 目录本身会让它自己的
`validate_skill.py` 把中间产物当成包内容扫到（多出莫名其妙的命中），也让"改进前后"混成一堆。
约定路径：`<工作区>/evolve/<skill-name>/`（工作区指你实际干活的目录，不是 skill 目录）。

工作目录结构：
```
<工作区>/evolve/<skill-name>/
├── baseline.md               # 改前冻结，不再修改
├── evolution-log.md          # 逐轮压缩记忆
├── round-1/
│   ├── prompt-1/
│   │   ├── prompt.md        # 原始 prompt
│   │   └── output/          # skill 产出
│   ├── prompt-2/
│   └── observations.md      # OTF 观察记录
```

`observations.md` 格式：
```markdown
## Prompt 1: [简述]
- 结果：[好/一般/差]
- 具体问题：[描述]
- 猜测原因：[指向 skill 中的哪段指令]

## Prompt 2: [简述]
...
```

### 👁 使用者视角穷举自审（角色切换法，实测极有效）

**这是本 skill 实测下来最锋利的一招，强烈建议作为标准路径里的常驻步骤。**

**核心要求（照做）：**

> 把自己当成这个 skill 的**真实使用者**——不是作者、不是评审——逐段、逐文件地"找茬"：凡是让使用者卡住、困惑、踩坑、觉得啰嗦、觉得不对劲的地方，全部记下来，然后**一一改正，直到你作为"使用者"再也挑不出任何一处毛病**。

**为什么它有效（作者盲区）：** 作者写自己的逻辑，自己永远觉得顺。真实使用者会从"明天我要拿它干活"的角度，暴露出作者看不见的问题——步骤顺序反了、某个约定没说清、示例对不上、README / 架构图 / 徽章 / 链接坏了、某段话术语堆砌看不懂、该有的兜底没有、触发词窄到根本不会被唤起。**Step 2 的 prompt 实测发现的是"跑出来的错"，使用者自审发现的是"用起来别扭"。** 两只眼互补。

**落地步骤：**

1. **切换角色** — 明确告诉自己：我现在不是写这个 skill 的人，我是明天要拿它干活的人。
2. **走查主路径** — 从 `SKILL.md` 开始，假装接到一个真实需求，一步步看指令能不能照着做、有没有断点、会不会误触发。
3. **走查 references/** — 每篇 reference 是否真能按需取到；里面的路径 / 文件名 / 章节引用对不对；有没有过期或自相矛盾；四目录（`references/` `evals/` `records/` `assets/`）约定是否都被遵守。
4. **走查交付物** — README、架构图、示例、徽章、链接是否都还成立、能否打开、是否和正文一致（这类"看着对、其实坏了"的毛病，只有使用者视角才会去点）。
5. **先列全，再改** — 把所有毛病列成一张清单，**不要边找边改**，避免改一处带偏另一处。
6. **一一改正 + 复验** — 按"使用者痛感"排序修，修完回到使用者视角复验，直到清单清空，且复验挑不出新毛病。

**在循环里的位置：**
- 和 Step 2 的 prompt 实测是**互补的两种发现手段**（一只看"跑出来对不对"，一只看"用起来顺不顺"）；清单产物直接喂给 Step 3 提炼模式。
- 也推荐作为**收敛前的最后一道放行闸**：在你宣布"可以了"之前，强制跑一遍使用者视角穷举自审。很多"作者觉得没问题"的残留，会在这一关被揪出来。

**什么时候它本身就是整轮打法：** 当你手头没有现成失败案例、也说不清哪有问题（Step −1 里"只有感觉不好用"那一类），这套"站在使用者角度把毛病全挑出来"就是最有效的启动方式——比凭空想测试 prompt 更直接。

### 第三步：提炼模式 — 从案例到规律（10 分钟）

**核心原则：不逐个修 bug，找共性根因。** 3 次规则：同类问题出现 ≥2 次就值得提炼为模式。

问题根因分层：

| 层级 | 表现 | 示例 |
|------|------|------|
| 触发层 | description 不准，该触发不触发 | 触发词太窄 / 和其他 skill 冲突 |
| 指令层 | 关键步骤缺失、指令模糊、优先级乱 | "分析网站"但没有说分析什么维度 |
| 资源层 | 缺必要的 reference/script/template | 引用不存在的脚本 |
| 架构层 | 职责太宽或太窄 | 一个 skill 干 5 件不相关的事 |

产出 `patterns.md`：
```markdown
# 错误模式表 — Round 1

## P01: [模式名称]
- 出现次数：N 次（prompt 1, 3, 5）
- 表现：[用户看到了什么问题]
- 根因：[skill 中的哪段指令导致的]
- 影响面：[高/中/低]

## 本轮改进优先级
1. P0x — [理由：影响面最大]
2. P0x — [理由：出现最频繁]
```

> **压缩比意识**：8 个具体问题提炼出 2 条模式，这很正常。2 条模式能覆盖未来新 prompt，比 8 个补丁更有价值。

---

### 第四步：改写 — JIT 原则（15-30 分钟）

**绝对不要一次性重写整个 skill。** 取优先级最高的 1-2 个模式，针对性改写。

**JIT 三原则：**
1. **最小改动** — 只改与目标模式直接相关的段落
2. **解释 why** — 每处改动都理解"为什么旧写法有问题"，说不清就回第三步再看
3. **可验证** — 改完后能用同样的 prompt 重跑，明确看到效果

**改写注意事项：**
- 给 agent 解释 why，而非堆砌 MUST/NEVER。agent 理解原因比记住规则更有效
- 检查重复劳动能否抽成 script，固化为 `scripts/` 下的脚本
- 保持信息密度，删掉水句（"请注意以下重要事项"之类）
- 长 skill 考虑分层：核心流程压进 SKILL.md，**目标 < 100 行**（渐进披露，避免加载烧上下文），细节放 references/；**硬性上限 < 500 行**，超过必须拆分（见「何时停止 / 不收敛诊断」）
- 我是在修真实观察到的问题，还是在凭直觉"优化"？
- 这个改动是通用的（覆盖未来新 prompt），还是只在拟合当前测试集？

产出 `changes.md`：
```markdown
# 改写记录 — Round 1

## 目标模式
- P01: [模式名]
- P02: [模式名]

## 改动清单
1. [文件:行号] 改了什么，为什么
2. ...

## 预期效果
- Prompt 1 应该不再出现 [具体问题]
```

**改写前 CHECKPOINT：**
- [ ] 备份原文件或确认在 git 分支上操作
- [ ] 结构大改前向用户展示方案，确认后再动手
- [ ] 每轮改进后展示 before/after 对比，暂停等用户确认

---

### 第五步：验证 — 格式校验 + 重跑 + 判断收敛

**5.0 自动化格式校验（先过格式，再验效果）：**
改完后先跑本 skill 自带的校验脚本，确认没破坏 SKILL.md 结构：
```bash
python <lifecycle>/scripts/validate_skill.py <目标 skill 目录> --mode improve
```
- **用 `--mode improve` 而不是默认的 `--mode create`**：改进一个既有 skill 时，它本来就没有 `evals/basic.md`、
  也不一定写了反模式小节——`create` 模式会要求补齐这些「本来就没有的东西」，
  把「改进」误判成「不合格」。`improve` 模式只要求**原有内容没被改坏**（已存在的 evals 被改坏仍会报错）。
- 新建 skill 才用默认的 `--mode create`（完整硬门）。
- 通过：继续看效果。
- 报错（name 规则 / description 尖括号 / frontmatter 非法 / 已有 evals 被改坏等）：**先修格式，再验效果**。
- 这是与 skill-create 一致的质量门——改进同样不能把格式改坏。

> 可选：`--json` 输出结构化报告，便于接入 CI；`--help` 查看完整用法。

**5.1 重跑 + 回归基线对比：**
用**同一批 prompt** 重跑改进后的 skill，并与改前的 baseline 输出逐条对比。对比两个维度：
- **目标模式是否消失**（我们要修的问题）。
- **原本通过 happy-path 的场景是否退化**（回归测试）——这一步防止"按下葫芦浮起瓢"。若某原本好的场景变差，记为"新问题（回归）"，按下方收敛表处理。

**基线怎么存（无外部评分器时唯一可行的做法）：**
改前先把「同一批 prompt + 改前输出」写进工作目录的 `baseline.md`，改后写 `round-N.md`，逐条并排对照：

```markdown
# baseline.md（改前，冻结不再改）

## Prompt 1：<触发语>
- 改前输出：<粘贴要点>
- 改后输出：<改进后填这里>
- 判定：目标模式已消失 / 减轻 / 未变 / 回归
```

> 把基线**写下来**是关键：只凭记忆对比会在两轮之后失真，导致「以为修好了其实没修」。

**收敛判据（WorkBuddy 环境可实际计算，不依赖任何外部评分器）：**
以「**新问题数**」和「**目标模式命中数**」为指标，二者都能人工逐条核对：

| 指标 | 怎么算 | 目标 |
|------|--------|------|
| 目标模式命中数 | 本轮目标模式在重跑输出中仍出现的次数 | 逐轮下降至 0 |
| 新问题数 | 重跑中冒出的、本轮之前没有的问题条数 | 恒为 0 |

- **新问题数 = 0 且目标模式命中数 = 0** → 收敛完成，停止迭代。
- **新问题数 > 0** → 本轮改动引入副作用，必须回滚或调整后再继续（不可带着回归进入下一轮）。
- **目标模式命中数不降** → 方向或力度不对，回到第三步重新提炼模式，不要继续加改动。

> 不要用「分数提升 Δ<2」作为停止判据：WorkBuddy 没有标准化评分器，分数无法计算，该判据不可执行（早期版本曾依赖 `dz benchmark` 的分数，现已不可用）。改用上表的两个可数指标。

**收敛判断标准：**

| 信号 | 含义 | 行动 |
|------|------|------|
| 目标模式问题消失 | 改进有效 | 进入下一轮处理剩余模式 |
| 问题减轻但没消失 | 方向对但力度不够 | 同一模式再改一轮 |
| 出现新问题 | 改动引入副作用 | 回滚或调整 |
| 连续 2 轮新模式数 = 0 | **收敛完成** | 停止迭代 |
| 修正量指数衰减（8→3→1） | 正常收敛曲线 | 继续 |
| 修正量不降反升 | 系统性问题被遗漏 | 回第三步重新分析 |
| 宣布"可以了"前未跑使用者视角自审 | 残留"作者盲区"型毛病 | 先跑一遍穷举自审再收尾 |

## Bootstrap：笔记自我增殖

每轮笔记不是用完就扔的草稿纸：

- **Round 2 开始前**：先读 Round 1 全部笔记，不重复已解决问题
- **积累 3 轮以上**：做一次递归压缩

```
Round 1-3 所有 observations（15+ 个具体问题）
  ↓ 压缩
5-8 条错误模式
  ↓ 压缩
2-3 条改进原则（这个 skill 最核心的"坑"是什么）
  ↓ 压缩
1 条洞察（这个 skill 的本质问题）
```

压缩结果写入 `evolution-log.md`（工作目录根下），是下次改进的起点。

---

## 沟通节奏

- **每轮开始前**：告诉用户这轮要解决什么模式、预计改什么
- **每轮结束后**：展示前后对比（用具体 prompt 的输出差异说话）
- **让用户做判断**：质量判断是用户的事，模式提炼是你的事

## 何时停止

- 用户说"可以了" → 停
- 连续两轮没有新模式 → 停
- 用户说"差不多了"、"够用了" → 停

不要追求完美。60%→90% 的投入产出比远高于 90%→95%。

## 交付物

1. **改进后的 skill**（覆盖原文件或写到新路径让用户确认）
2. **evolution-log.md**（压缩记忆，下次继续）
3. **一句话总结**：改进了什么、为什么、效果如何
4. **更新版本号** — 改完必须 bump SKILL.md frontmatter 的 `metadata.version`（建议语义化：补丁级 `+0.0.1`，结构性改动 `+0.1.0`），让用户能区分新旧版；这与 skill-create 的版本管理口径一致。

## 思维检查清单

每轮改进前过一遍：
- [ ] 我先判过路径了吗？（能说出「哪个输入 → 哪个错误输出」→ 直接 FIX，别跑五步循环）
- [ ] 我跑过"使用者视角穷举自审"了吗？（站到真实使用者座位上，把毛病全挑出来、改到挑不出为止——实测最锋利的一招，详见 `references/skill-improve.md` 的「使用者视角穷举自审」）
- [ ] 我是在修真实观察到的问题，还是在凭直觉"优化"？
- [ ] 这轮改动能被具体的 prompt 验证吗？
- [ ] 我是不是在同时改太多东西？（一次只改一件事）
- [ ] 我是在给 agent 解释 why，还是在堆 MUST/NEVER？
- [ ] 这个改动是通用的（覆盖未来新 prompt），还是只在拟合当前测试集？
- [ ] 我有没有删掉不起作用的旧指令？（skill 应该越改越精炼，不是越改越长）

## 异常处理

| 触发条件 | 一线修复 | 兜底 |
|---------|---------|------|
| 目标 skill 不存在或路径错误 | 确认名称拼写，检查 skills 目录 | 询问用户提供正确名称 |
| 改进 3 轮仍无改善 | 检查是否修"真实问题"而非"直觉优化" | 尝试探索性重写 |
| 测试 prompt 跑不通 | 简化 prompt 到最小可用版本 | 手动模拟执行流程 |
| skill 该触发但未触发 | 检查 description 和触发词 | 对比触发成功的类似 skill |
| 3 轮还不收敛 | 职责太宽/测试矛盾/能力限制 | 拆分 skill 或诚实告知 |

## 🛑 CHECKPOINT：关键决策前确认

| # | 节点 | 触发条件 | 确认内容 |
|---|------|---------|---------|
| CP-I1 | 开始改进前 | 用户说"帮我改进skill" | 确认走标准路径还是FIX模式 |
| CP-I2 | 改写前 | 完成模式提炼 | 展示要改的模式和改动方案，等用户确认 |
| CP-I3 | 每轮改写后 | 完成一轮改写 | 展示before/after对比，等用户说好再继续 |
| CP-I4 | 收敛后 | 连续2轮无新模式 | 展示改进总结，建议下一步（审查/继续） |

**违反CHECKPOINT的信号：** 如果你在没有用户确认的情况下连续改了2轮以上，立即停下，回溯到CP2。

## 编辑已装的 marketplace skill（WorkBuddy 平台特有）

若目标 skill 是从 marketplace 安装的（非本地创建），改完并**成功保存后**必须标记 `userModified`，否则平台自动更新会静默覆盖你的改动：

1. 在目标 skill 目录找 marketplace 元文件，名为 `_skillhub_meta.json`（BuiltinMarket / SkillHub 源）或 `_knot_meta.json`（Knot 源）。
2. 用 Read + Write 读取该 JSON，把 `"userModified": true` 写回（原无该字段则新增）。
3. 保存后告知用户：改动已保存，未来 marketplace 更新会先询问再覆盖。

**注意：**
- 只在文件真的写盘后再标记，不要提前或推测性标记。
- 本地创建的 skill（目录里没有上述元文件）→ 跳过此步，无需标记。
- 本小节只针对"编辑已有 skill"；从零创建（skill-create）不涉及。

## 改进后下一步

改进完成后，建议用户：

| 下一步 | 说明 | 使用的子skill |
|--------|------|--------------|
| 审查skill | 确认安全性后再安装 | skill-vet |
| 继续改进 | 还有其他问题需要修复 | skill-improve |
| 直接使用 | 如果改进效果满意 | - |

**建议流程：** improve（迭代2-3轮） → vet → publish

## 与skill-create的衔接

如果改进过程中发现skill需要大改：

| 情况 | 处理 |
|------|------|
| 职责太宽，需要拆分 | 用skill-create (DERIVED) 拆分成多个skill |
| 发现更好的模式 | 用skill-create (CAPTURED) 提取新skill |
| 与现有skill重复 | 用skill-create (DERIVED) 合并 |

## 🚫 不要做的事

| 不要 | 原因 | 正确做法 |
|------|------|---------|
| 一次性重写整个 skill | 多变量同时变无法归因 | 每轮只改 1 个维度 |
| 未观察到问题凭直觉优化 | 可能越改越糟 | 必须基于真实测试 |
| 硬凑 N 轮 | 新问题数连续 2 轮为 0 且目标模式命中数已归零 → 已触顶 | 见好就收 |
| 修表面 bug 不提炼模式 | 补丁覆盖不了新 prompt | 找共性根因 |
| 改 skill 前不备份 | 改坏了无法回滚 | git 分支或备份 |
| 改进后不建议审查 | 安全风险 | 建议走skill-vet |
